# Translations

How the UI is translated, the terms to use in each language, and how to add a string or a
language. The short version for agents is in `AGENTS.md`, Translations. The system is the same as
Postino's (`~/dev/postino/docs/i18n.md`), with Nastro's own files, tests and glossary.

Languages: English (`en`, the source and the fallback), Spanish (`es`), Galician (`gl`) and
Italian (`it`).

## Decisions

| Topic | Decision |
| --- | --- |
| Library | [`rust-i18n`](https://crates.io/crates/rust-i18n) 4. `gpui-component` already uses it for its own strings, so one `rust_i18n::set_locale` call switches both Nastro's strings and the library's (input context menu, ...). Translations are embedded in the binary at compile time and a lookup is a hash map read. |
| Why not Fluent | The four languages only need "one" and "other" plurals, which a two-key convention covers, and a second i18n system next to the one `gpui-component` ships is not worth it. |
| OS language | [`sys-locale`](https://crates.io/crates/sys-locale). `get_locales()` returns the user's preferred languages in order. The first one whose primary language subtag is supported wins, and none matching means English. |
| Regions | Variants map to the base language (`es-MX`, `es_ES.UTF-8`, `it-CH`, `gl-ES`). |
| Setting | `language = "auto" \| "en" \| "es" \| "gl" \| "it"` in `settings.toml`, default `auto`. In Preferences, the first section ("Language"). Options are written in their own language (English, Español, Galego, Italiano). The first one is "Automatic" translated, plus the detected language in parentheses. |
| Applying a change | Live, no restart. `Shell::set_language` calls `rust_i18n::set_locale` (through `state::locale::apply`), then `views::relocalize` re-applies every string cached outside `render`, then `cx.refresh_windows()`. |
| Numbers | Localized with CLDR data through [`icu_decimal`](https://crates.io/crates/icu_decimal) 2, in `state::number` (`format_integer`, `format_decimal`): the decimal separator of `44.1 kHz` and `1.5x`, the thousands separator of bitrates in `kbps`. Unit symbols stay as they are. |

## Files and keys

- One YAML file per area under `crates/nastro-app/locales/`: `menu` (the menu bar and its
  items), `player` (the panel titles, the player and equalizer buttons, the display, the
  equalizer preset names), `playlist` (the playlist panel and its menus) and `preferences`
  (Preferences, the setting choices and About). Parallel work on different areas never edits the
  same file.
- Format `_version: 2` (the one `gpui-component` uses): every key lists its four translations
  together, so adding a key means writing all languages in one place.
- Keys are dotted, area first, lowercase snake case: `menu.play.seek_forward`,
  `playlist.sort_title`, `settings.log_level.warn`. The equalizer preset names are
  `eq.preset.<id>`, where `<id>` is the id of the preset in `nastro-core` (`hip_hop`,
  `bass_boost`, ...), so a new preset needs its name in all four languages.
- Plurals are two keys, `<key>.one` and `<key>.other` (`playlist.tracks.one`,
  `playlist.tracks.other`), read with `state::locale::plural(key, count)`, which passes `count`
  as an argument.
- Arguments use `%{name}` in the YAML and `t!("key", name = value)` in code
  (`playlist.default_name`, `preferences.skin_hint`).
- YAML values that are `ON`, `Off`, or anything YAML would read as a boolean are quoted
  (`"ON"`, `"Off"`).

## In code

- `main.rs` has `rust_i18n::i18n!("locales", fallback = "en");` at the crate root, so `t!` works
  in every module of `nastro-app`.
- `state/locale.rs` is plain Rust with unit tests: `Language`, `LanguageChoice`,
  `match_language(tag)`, `detect(preferred)`, `resolve(choice)`, `apply(language)`,
  `plural_key` and `plural`.
- In views, `t!("player.shuffle")` directly in the element tree. It returns a
  `Cow<'static, str>`; wrap it with `SharedString::from(...)` where an API needs it.
- State functions that return labels (`ThemeChoice::label`, `LogLevel::label`,
  `VisualizerMode::label`) build them with `t!` at call time. Never store a translated string in
  state that outlives a render, except where an API forces it.
- **Cached strings:** the playlist filter placeholder is set once when the field is created.
  `PlaylistPanel::relocalize` sets it again, and `views::relocalize` forwards to the main window.
  Menus are built when they open, so they pick up the current language.
- **Performance:** a `t!` lookup per element per render is fine. Do not translate inside the
  closure that renders the track rows.
- **Numbers shown to the user** go through `state::number`. Never use it in logs or in values
  written to a file (`skin_scale` in `settings.toml` is the plain number `1.5`, the label `1,5x`
  is for the screen only).

## What is translated

Every user visible string produced by `nastro-app`: the menus, the labels of the buttons, the
panel titles, the display text (the idle message, `STEREO` and `MONO`), the playlist texts, the
equalizer preset names, Preferences and About.

Not translated:

- Log messages: they are for bug reports and stay in English.
- Errors produced by the library crates (decoding errors, audio device errors, skin errors).
  They are shown verbatim, for example in the display when a track fails.
- Codec names and units: `FLAC`, `MP3`, `kbps`, `kHz`, `CH`, `dB`, `Hz`, and the band labels
  `31` to `16k`. Only the decimal separator follows the language.
- Keyboard shortcut labels (`Ctrl`, `Cmd`, `Alt`).
- The names of the built-in skins (Silver, Graphite, Porcelain, Nebula) and of user skins.
- The wording of the user guide, which is in English only for now.

## Tests

- The locale is process wide and `cargo test` runs tests in parallel, so **no test may call
  `rust_i18n::set_locale`**. A test that needs a language uses `t!("key", locale = "es")`.
- `state/locale.rs` tests check that every key has a non-empty value in all four languages, that
  no language has a key English lacks, that every `%{arg}` placeholder of the English text
  appears in each translation and no extra ones, that no text contains an em dash, that plural
  keys come in `.one` and `.other` pairs, and that every literal `t!("key")` used under `src/`
  exists. A missing key would otherwise render the key itself at runtime.
- `views/equalizer.rs` has the test `every_preset_has_a_name_in_every_language`: preset names are
  looked up with a key built at run time (`eq.preset.<id>`), which the literal key test cannot
  see, so this one checks every preset of `nastro-core` against all four languages.

## Adding a string

1. Add the key with `en`, `es`, `gl` and `it` to the YAML file of its area.
2. Use `t!("area.key")` in the code. If the string is cached outside `render`, add it to the
   relevant `relocalize`.
3. Run `make test`: the completeness tests fail on a missing language, a placeholder mismatch or
   an unknown key.
4. If the string is a label on the skin (`ADD`, `SHUFFLE`), check that the longest translation
   still fits its button.

## Adding a language

1. Add the code, native name and matching rules to `Language` and `LanguageChoice` in
   `state/locale.rs`.
2. Add the translation to every key of every YAML file. The completeness test lists what is
   missing.
3. Add the language to the Preferences list and extend the glossary below.
4. Check the longest labels, above all the uppercase ones on the skin buttons and the preset
   names in the PRESETS menu. Fix clipped text with an ellipsis or a shorter word, never by
   shrinking the font.

## Glossary

Use these terms consistently, copied from the YAML files. Nastro is a consumer music player:
keep short, friendly and neutral wording, use the infinitive or the noun on buttons and menus
(`Reproducir`, `Engadir`, `Aggiungi`), not the imperative with "tú" or "usted". The labels on
the skin buttons are uppercase (`ADD`, `SHUFFLE`, `PRESETS`) and must stay short. Spanish is
neutral (Spain and Latin America). Galician follows the RAG normative. Italian keeps the English
word "skin", Spanish and Galician say "aspecto".
